# Modo DIA Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agregar un modo DIA activable desde la interfaz que, entre 06:00 y antes de 16:00, apague solo los LEDs de efectos para ahorrar bateria mientras mantiene el rastreo de movimiento y los LEDs de alerta/estado.

**Architecture:** DIA debe ser una compuerta de ahorro persistente e independiente del modo visual actual (`speed`, `geofence`, `simple`, `show`), no un quinto modo que reemplace esos modos. La compuerta vive en configuracion, calcula si la hora local GPS esta dentro de ventana diurna, y `led_ui` la usa para apagar el cuerpo de las tiras sin tocar GPS, almacenamiento de tracks, WiFi, portal ni LEDs de estado.

**Tech Stack:** PlatformIO, Arduino framework, ESP32-S3, Adafruit NeoPixel, ArduinoJson, Preferences/NVS, GPS NMEA RMC/GGA.

---

## Evidencia Del Codigo Actual

- `src/main.cpp` declara el proposito del firmware: leer GNSS, computar distancia/velocidad, servir portal WiFi y manejar SK6812 como UI. El loop llama siempre `gps::tick()`, `gps::save_if_due()`, `gps::track_tick()`, `wifi_mgr::tick()`, `led_ui::tick()` y `portal_http::handle_client()`. Por eso el ahorro de DIA debe estar dentro de `led_ui`, no deteniendo el loop principal.
- `include/config.h` define `MODE_SPEED`, `MODE_GEOFENCE`, `MODE_SHOW`, `MODE_SIMPLE`, `LED_STRIP_COUNT`, `LED_STATUS_COUNT`, `LED_BRIGHTNESS`, `LED_UPDATE_MS` y los limites GPS. No hay constantes de DIA, zona horaria, NTP ni RTC.
- `include/config/runtime_config.h` y `src/config/runtime_config.cpp` guardan la configuracion persistente actual. `version()` es `4`; cualquier campo persistente nuevo debe migrar a version `5` sin perder configuraciones existentes.
- `src/led/led_ui.cpp` separa visualmente `LED_STATUS_COUNT` LEDs reservados al inicio de cada tira. `paint_status_leds()` pinta estado WiFi/GPS/error. Los efectos del cuerpo arrancan en `seg_start = LED_STATUS_COUNT`. Esto permite apagar efectos sin apagar alertas.
- `src/led/led_ui.cpp` tiene una excepcion llamada `homogeneous_mode` cuando WiFi esta apagado y GPS ya estuvo estable; en ese caso aplica efectos a toda la tira desde indice `0`. DIA debe tener prioridad sobre esa excepcion para no encender LEDs de estado como parte del efecto.
- `src/gps/gps.cpp` parsea hora y fecha desde RMC. Expone `gps::current_date()` y `gps::last_update_min()`, pero `last_update_min()` se actualiza solo con fix confiable. Esa hora parece UTC de GPS/NMEA; para Colombia/Bogota se debe convertir a hora local con offset configurable o constante.
- `src/wifi/wifi_mgr.cpp` ya puede apagar el radio WiFi en algunos estados (`wifi_off_state`), pero el usuario pide que el rastreador siga funcionando. DIA no debe cambiar politica WiFi salvo que se decida explicitamente en otro feature.
- `src/web/portal_http.cpp` expone `GET/POST /api/config` y `POST /api/mode`; `src/web/pages.cpp` contiene la UI de configuracion y cards de modo. DIA debe aparecer como interruptor/opcion adicional, no sustituir los cards existentes.

## Requisitos Confirmados E Inferidos

- Activacion manual: el usuario activa "Modo DIA" desde la interfaz.
- Ventana automatica: si DIA esta activado y la hora local es mayor o igual a 06:00 y menor que 16:00, los LEDs de efectos se apagan.
- Fuera de ventana: si DIA esta activado pero son antes de 06:00 o desde 16:00 en adelante, el modo visual normal sigue funcionando.
- Alertas: los 4 LEDs de alerta siguen funcionando. En este firmware eso equivale a `LED_STATUS_COUNT` por tira; con `LED_STRIP_MODE = 2` y `LED_STATUS_COUNT = 2`, son 2 por tira = 4 fisicos.
- Rastreo: GPS, metricas de distancia/actividad, track storage y portal siguen funcionando igual.
- Hora no confiable: si no hay fecha/hora GPS valida, DIA no debe apagar efectos por accidente. Debe reportar estado "hora no disponible" y mantener comportamiento normal hasta tener hora valida.

## Decision Recomendada

Implementar DIA como `day_mode_enabled` + evaluador horario, no como `MODE_DAY`.

Razones:
- Evita contradiccion con los modos existentes. El usuario puede seguir usando `speed` o `geofence` para la noche y DIA solo corta el cuerpo LED durante la ventana diurna.
- Reduce riesgo de romper `parse_mode()`, `mode_name()`, endpoints existentes y cards del dashboard.
- Permite indicar en `/api/dev` si DIA esta armado, activo, inactivo por horario o inactivo por falta de hora.

Alternativas evaluadas:
- **Nuevo `MODE_DAY`:** mas simple en UI, pero se pierde el modo visual que debe volver despues de las 16:00. Requiere recordar modo anterior o anidar modos.
- **Bajar brillo a 0:** apagaria tambien los LEDs de alerta porque `setBrightness(0)` afecta toda la tira. Contradice el requisito de mantener 4 alertas.
- **Apagar radio WiFi/GPS:** ahorra mas, pero rompe la premisa de rastrear y puede hacer el portal inaccesible. Queda fuera de alcance.

## Contrato De Comportamiento

| Condicion | Efectos cuerpo | LEDs estado/alerta | GPS/track | WiFi/portal |
|---|---:|---:|---:|---:|
| DIA desactivado | normal | normal | normal | normal |
| DIA activado, hora local 06:00-15:59 | apagados | normal | normal | normal |
| DIA activado, hora local <06:00 o >=16:00 | normal | normal | normal | normal |
| DIA activado, sin fecha/hora confiable | normal | normal, idealmente con dev status | normal | normal |
| Welcome al boot | recomendado: permitir terminar welcome, luego aplicar DIA | normal | normal | normal |
| `MODE_SHOW`/`MODE_SIMPLE` durante DIA activo | cuerpo apagado | normal | normal | normal |
| `homogeneous_mode` durante DIA activo | no debe pintar toda la tira | normal | normal | normal |

## Riesgos Y Controles

- **Hora UTC vs hora local:** RMC entrega hora UTC. Para Colombia se necesita offset `-300` minutos si el collar opera en America/Bogota. Plan inicial: constante `DAY_MODE_TZ_OFFSET_MIN = -300` en `config.h`; si se desea viajar, convertirlo luego en campo configurable.
- **Medianoche y cambios de fecha:** la ventana 06:00-16:00 no cruza medianoche; basta convertir minutos UTC a minutos locales con modulo 1440.
- **No hay hora valida al boot:** `gps::last_update_min()` inicia en `0`, que tambien podria significar 00:00. Se requiere exponer un booleano explicito de tiempo valido, por ejemplo `gps::has_time()`, basado en `current_date_yyyymmdd != 0` y ultimo RMC confiable reciente.
- **Perder alerts por clear completo:** si se limpian todos los LEDs despues de pintar estado, se apagan alertas. La secuencia correcta en DIA es limpiar solo `seg_start..end`, luego `paint_status_leds()`, luego `show_leds()`.
- **Estado persistente y migracion:** al subir version NVS a `5`, versiones `4`, `3`, `2` deben migrar con `day_mode_enabled = false` por defecto.
- **Consumo de bateria limitado:** apagar LEDs ahorra bastante, pero el firmware seguira usando GPS, MCU y WiFi segun politica existente. No vender esto como "modo ultra bajo consumo".

## Fase 1: Modelo De Hora GPS Local

**Files:**
- Modify: `include/config.h`
- Modify: `include/gps/gps.h`
- Modify: `src/gps/gps.cpp`

- [ ] Agregar constantes:
  - `DAY_MODE_START_MIN = 6 * 60`
  - `DAY_MODE_END_MIN = 16 * 60`
  - `DAY_MODE_TZ_OFFSET_MIN = -300`
  - `DAY_MODE_TIME_STALE_MS = 300000` como tolerancia inicial de 5 minutos sin RMC confiable.

- [ ] Exponer en `gps.h`:
  - `bool has_time();`
  - `uint16_t local_time_min(int16_t offset_min);`
  - `unsigned long last_time_ms();`

- [ ] En `gps.cpp`, actualizar `gps_last_time_ms` cuando `date_yyyymmdd != 0`, `parse_time_min()` fue valido y el fix es confiable. No usar `last_update_min_val == 0` como indicador booleano porque 00:00 es hora valida.

- [ ] Implementar conversion local con modulo seguro:
  - `local = (utc_min + offset_min) % 1440`
  - si queda negativo, sumar `1440`.

- [ ] Criterio de hora confiable:
  - `current_date_yyyymmdd != 0`
  - `gps_last_time_ms > 0`
  - `millis() - gps_last_time_ms <= DAY_MODE_TIME_STALE_MS`

- [ ] Verificacion esperada:
  - UTC 10:59 con offset -300 => 05:59, DIA inactivo.
  - UTC 11:00 => 06:00, DIA activo.
  - UTC 20:59 => 15:59, DIA activo.
  - UTC 21:00 => 16:00, DIA inactivo.
  - Sin RMC confiable => `has_time() == false`.

## Fase 8: Criterios De Aceptacion

- DIA se activa/desactiva desde la interfaz y persiste en NVS.
- Entre 06:00 y antes de 16:00 hora local, con DIA activado y hora GPS confiable, no hay efectos en el cuerpo de las tiras.
- Los 4 LEDs de alerta siguen funcionando durante DIA activo.
- GPS, distancia, velocidad, historial de sesiones, track points y portal siguen operativos.
- Si no hay fecha/hora confiable, DIA no apaga efectos y el diagnostico lo explica.
- La configuracion existente de modos, rangos, efectos, WiFi y GPS migra sin perderse.
- `pio run -e seeed_xiao_esp32s3` pasa.

## Fuera De Alcance Inicial

- Configurar horario DIA desde UI.
- Detectar luz real con sensor.
- Deep sleep o apagado de GPS/WiFi.
- NTP/RTC externo.
- Cambiar politica de AP/STA existente.

## Revision Del Plan

- Cobertura: incluye configuracion, UI, API, LED, hora GPS, diagnostico, migracion y pruebas.
- Contradicciones evitadas: DIA no es un modo visual nuevo; por eso no compite con `speed/geofence/simple/show`.
- Principal riesgo restante: si el GPS entrega UTC y el collar se usa fuera de Colombia, el offset fijo sera incorrecto. Para este proyecto se asume America/Bogota por el contexto del entorno actual.
