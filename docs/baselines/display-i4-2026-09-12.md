# Display I4 — software consolidation and USB-only bench

Date: 2026-09-12. **I4 remains in progress.** Work started from clean commit
`238b58e6e777c99bf986c0bb07800adb9ad4d03b`. The owner authorized using the
connected board and simulated screen data, explicitly confirming that neither
GNSS nor LED strips were soldered. The results below cover that limited setup;
they do not close the combined collar acceptance gate.

## Delivered increment

- Stage 3 adds `f`: a labeled **RGB DOG DEMO** cycling through searching,
  stationary/moving fix, poor quality, stale and recovered fix. `v` restores
  live data. Fixtures enter only the display snapshot, never GPS, LED policy,
  routes, daily totals or configuration storage. Reset starts in live mode.
- The optional `tools/display_bench.py` captures USB logs, schedules bounded
  LCD commands and summarizes observations without declaring acceptance.
  Joined serial records are counted and excluded from numeric/state analysis;
  raw reset/fatal markers remain visible. Saved-log analysis requires only Python.
- Native tests execute the real configuration codec, A/B save/load and LED
  apply path for Classic and stage 3: ten changes and fresh-process reloads per
  variant, plus recovery after a truncated write. Preferences, radio and LED
  transport are fakes. Requested brightness persists independently of the
  stage-3 transport cap. This is not a physical NVS or HTTP-handler test.
- Root Playwright now excludes `tests/portal-e2e/`, which belongs to the
  separate application config and its fixture lifecycle. The embedded AP suite
  no longer imports those environment-dependent tests.

Reproduction and remaining acceptance are in the

## Device identification, preservation and boot

COM6 responded as ESP32-S3 revision 0.2 with embedded 8 MiB PSRAM, 40 MHz
crystal, USB Serial/JTAG and 16 MiB flash. Firmware independently reported
16,777,216 flash bytes and 8,388,608 PSRAM bytes. These observations support
the configured memory profile; they do not identify the PCB silkscreen revision.

Before flashing, the original partition table was read. NVS, OTA data, both app
slots, SPIFFS and coredump all fit within the first 4 MiB. Stub-based reads failed
repeatedly at address `0x79000`; ROM `--no-stub` reading completed the original
**4,194,304-byte backup**, covering every mapped original partition. This is
not a full 16 MiB backup. No full-chip erase or restoration was performed.

Backup SHA-256:
`9ce01f857af79eeb2bb57dcc3103e59e4f038a42c02ab269dfc8992fa940d727`.

I0 was uploaded and booted successfully through **five requested USB resets**.
Each reported the expected flash/PSRAM, `sys_out=1`, `lcd=off` and inactive
external I/O. This is not five power/battery cycles or a completed I0 soak.
Stage 3 was then uploaded with esptool hash verification. Its tested image is
1,237,792 bytes, SHA-256:
`b0bee654b1896d9488faa7f597cbbb199b4fb80f2e82b3017a10d45c8e44b90a`.
The final seven-target build produced the same stage-3 binary hash.

## Ten-minute LCD observation

USB-powered board, no external GNSS/strips; stage-3 image above. Capture lasted
600.187 seconds. Commands: `f` at 0 s, `r` at 5 s, backlight `b` at 180/240 s,
service pause/resume `d` at 300/360 s, then `r` at 365 s. Scheduled commands were
sent within 0.172 seconds of those offsets. Final reported state was ready,
enabled, backlight on and demo active. The board was left in that state.

| Observation | Measured result and scope |
| --- | --- |
| Valid reports | 1,007 LCD, 20 SYS and 1,005 I3; SYS timestamps span 570 s |
| Malformed records | One joined I3 line at capture start; excluded in reviewed summary |
| Startup LCD initialization | 633,766 µs, separate from normal drawing |
| Final normal drawing window | 140 drawing ticks / 140 rows; maximum draw and service 4,597 µs; p95 bucket upper bound 5,000 µs |
| Whole-capture maximum LCD service | 32,447 µs, including manual full redraws |
| Maximum reported cumulative p95 bound | 50,000 µs; this is not a percentile computed over the entire capture |
| Free heap | First/last 221,548 bytes; minimum observed 220,156 bytes |
| Lifetime minimum heap | Final 219,404 bytes |
| Log drop counter | 51,878 bytes both first and last: zero additional drops in observed SYS window |
| Actual GPS | Only `no-data`; RX and overflow counters remain zero |
| Reset/fatal observations | No boot markers, clock regressions or fatal markers in captured logs |

The joined first record is consistent with a partial buffered message around
monitor reconnection; its exact cause was not established. The parser regression
test prevents its `state=n[I3]` fragment from being reported as a GPS state.
The original capture/JSON are preserved; `lcd-demo-10min-reviewed.json` contains
the corrected analysis, while capture duration/command timestamps remain in the
original JSON. No second ten-minute run was needed for this parser correction.

Reported enable/backlight transitions and SPI timings do not prove visible
pixels, orientation or color order. The owner subsequently confirmed seeing
the working demo, enabling the [I5 increment](display-i5-2026-09-12.md); specific
color-bar/orientation acceptance was not separately recorded. This LCD
uses 1 Hz data sampling and partial row drawing; these timings are not an FPS
benchmark or validation of animated LVGL. Stable idle heap is not proof against
leaks under settings/export/GNSS load. Zero UART RX cannot validate capacity.

## Remaining implementation gate

The host exposes Ethernet but no available Wi-Fi adapter. Actual embedded
HTTP, hardware save/reboot/read and route transfers were therefore not exercised;
browser mocks are not substitutes. Wokwi runtime remains unavailable locally
without its CLI/token. PCB revision, panel orientation/colors, electrical/current
behavior, battery and real GNSS/strips also remain open.

Continue the guide's physical I0–I3 checks, then I4's 30-minute combined run,
ten mode changes, three physical save/restart/read cycles, populated route
exports and outdoor check. A phone on the board's AP can enable the portal
portion before soldering, but cannot close the GNSS/LED load checks. I5's LVGL
components/simulator and I6's visual refinement remain subsequent increments.
