# Display I1 — two-strip LED bench diagnostic

Date: 2026-09-12. **Software implemented and locally verified; physical I0/I1
acceptance remains open.** The owner's instruction to continue implementation
was used to prepare I1 software without treating the pending I0 bench test as
passed. No board was flashed and no current/color/waveform measurement is claimed.

## Starting point and scope

Work started at `3fa9e7bff27b0cc6e10c78eea0a68d966c7294b8`, with the uncommitted
[I0 changes](display-i0-2026-09-12.md) already present. During this run HEAD
advanced to `9b399760e84d164e05c10e42a0131b711ef3a5c6`, which includes the I0/I1
firmware/configuration changes compiled here. The new LED native test and final
documentation updates remain local additions/changes at recording time. Existing
local work was retained. Python 3.11.9, PlatformIO 6.1.19 and native `g++` were
used on Windows; CI remains Python 3.13. Platform/core, NeoPixel, ArduinoJson,
partition layout and product configuration defaults were not changed.

The new `waveshare_lcd169_ledcheck` environment selects bringup stage 1 using
the same board profile and `main.cpp`. The stage-0 environment remains separate.
Stage 1 adds the small command/sequence controller plus the existing `LedBus`,
`rgb_to_rgbw` and `PowerLimiter`; it excludes normal LED policy/welcome, scenes,
GPS, Wi-Fi and application storage. Stages 2+ remain rejected at compile time.

Behavior:

- Boot sends black to both configured strips and waits for a fresh USB command.
- `1`: 30-second one-pixel sequence, A → B → both, each R/G/B/W/off at 2 seconds
  per step; all remaining configured pixels are black.
- `f`: repeats that sequence over the full configured length for at most
  15 minutes. Available only after all one-pixel steps were sent in this boot.
  A large skipped interval cannot mark unsent steps complete. Completion is
  a software observation, not acknowledgment from the LEDs or the operator.
- `0`: transmits black and stops. It wins over start commands in the same input
  batch; remaining queued commands are drained before accepting fresh commands.
- USB disconnection stops and sends black; reconnection drains stale input and
  does not restart. Input processing is bounded to 16 characters per tick.
- `?` and periodic reports show scope/bus/color plus estimated-current data.
- Brightness is fixed at 16/255. The existing estimator is enabled with its
  default model/budget in RAM; no persisted settings are read or modified.

The configured strip length remains 24 per bus. White is converted to the W
channel by the existing bus, rather than adding another color implementation.
The diagnostic's solid colors exercise that transport; normal product Simple
mode already exists and still requires physical acceptance with the actual
Waveshare integration. No new product effect or scene was added.

## Verification

From `Platformio/Dog-RGB`, using the existing local PlatformIO executable when
`pio` is absent from PATH:

```powershell
pio run -e seeed_xiao_esp32s3 -e wokwi -e waveshare_lcd169 -e waveshare_lcd169_bringup -e waveshare_lcd169_ledcheck
python -m unittest discover -s test -p "test_*.py" -v
```

Results: **5/5 builds and 135/135 host tests passed**. Build output contains no
compiler warnings/errors. The first new native-test compile encountered unused
AP string-pointer warnings from the shared `config.h`; the harness now suppresses
only that header's unused-variable warning and retains `-Werror` for the code
under test. Product configuration was not altered to accommodate the harness.

The new native test executes the real diagnostic controller, common bringup
entry, LED bus, RGBW conversion and limiter with a fake NeoPixel transport and
USB clock/input. It verifies all 15 one-pixel steps, A/B independence, all
unselected pixels black, W-only white, fixed brightness, full-length output,
no repeat transport for unchanged steps, command precedence, bounded draining,
USB loss/reconnection, first-test gating, automatic stop and `millis()` rollover.
A separate synthetic 201 mA budget within the same harness verifies that the
real bus applies the limiter's reduced scale and estimated current stays within
that test budget. It is not a measured-current test.

Defined ELF symbols and `pio pkg list` were inspected for all five environments:

- Product binaries contain no `bringup::` functions and retain the GPS core.
- Stage 0 contains neither the LED check nor `LedBus`.
- Stage 1 contains `led_check::tick`, `LedBus::show` and `PowerLimiter::evaluate`.
- Neither diagnostic contains GPS, normal LED policy, scene runtime, Wi-Fi
  manager or application storage initialization symbols.
- No graphics dependency was introduced.

The existing firmware CI matrix now includes the stage-1 environment with its
own artifact name. YAML parsing and the five-target matrix check passed locally;
remote GitHub Actions execution is not claimed. Documentation links and
`git diff --check` were also checked. Raw local logs/package inventories and
