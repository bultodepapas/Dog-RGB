# ADR-0008: Resource-level HLC last-write-wins configuration sync

**Status:** Accepted

**Date:** 2026-08-13

**Scope:** Bidirectional AP/web configuration convergence, clock uncertainty, atomicity, desired/reported state, and first-release exclusions.

## Context

A collar can be configured while offline through its AP and later through the website. Either side may edit before learning the other state; HTTP responses may be lost or replayed; the collar may reboot; and ESP32 wall time may be missing or wrong. The requested product rule is last-write-wins (LWW): the most recent change should replace an older one regardless of origin.

Whole-document LWW would make an unrelated brightness edit overwrite a newer GPS profile. Per-field LWW would allow semantically coupled arrays/settings to combine into an invalid profile. A plain wall-clock timestamp is unsafe when the device has no trusted time, and a server sequence alone cannot represent an AP edit made offline.

There is also a fundamental limit: when two offline actors have no common trusted clock, no protocol can reconstruct their true real-time edit order from arrival order alone. The design must be deterministic and honest about that ambiguity instead of pretending it has perfect chronology.

## Decision

### Coherent sync resources

LWW applies to an entire validated resource, not the complete `RuntimeConfig` and not arbitrary individual fields:

| Resource key | Atomic fields | First release |
| --- | --- | --- |
| `brightness` | `brightness` | Sync in the Phase 3 vertical slice. |
| `visual_mode` | `mode`, `day_mode_enabled` | Add after brightness convergence is proven. |
| `speed_profile` | all nine `ranges` plus all ten `effects` records | Add as one coherent resource. |
| `simple_effect` | `single.effect_id`, speed, intensity, base RGB | Add as one coherent resource. |
| `gps_quality` | quality, satellite, HDOP, GGA age, segment and HDOP-factor gates | Add as one expert resource. |
| `geofence_policy` | `fence_max_m` only | Sync without Home coordinates. |

The following remain local-only for the first full cloud release:

- `home_location`: sensitive and tightly coupled to physical “set from current trusted fix” semantics;
- `power_model`: safety/calibration values must not be changed remotely until hardware calibration and stronger authorization UX exist;
- AP SSID/password and mDNS identity;
- station Wi-Fi SSID/password;
- local portal PIN; the device cloud credential is also excluded from configuration resources/history and is used only in verified-TLS device authentication.

This is an affirmative product/security decision, not a missing mapping. A later release requires a new ADR and threat/safety review before syncing Home or power calibration.

### Winner envelope

Every synced resource uses a canonical envelope containing at least:

- `resource_key` and resource schema version;
- complete validated resource value and canonical body hash;
- unique `mutation_id` generated by its actor;
- server-derived `actor_id` (stable device ID or authenticated user actor ID);
- Hybrid Logical Clock (HLC) tuple `(physical_ms, logical)` and clock-quality/audit facts;
- optional `base_server_version` supplied by the editor;
- monotonically increasing `server_version` assigned only when the canonical winner changes;
- origin, accepted/received timestamps, and desired/report status.

The total order is lexicographic `(physical_ms, logical, actor_id_bytes)`. Actor IDs use one canonical byte representation and are derived from authenticated identity; a client cannot choose a tie-break ID.

Given local state `(p, l)`, remote `(rp, rl)`, and bounded physical observation `now`, HLC receive/update follows:

```text
p2 = max(p, rp, now)
if p2 == p and p2 == rp: l2 = max(l, rl) + 1
else if p2 == p:         l2 = l + 1
else if p2 == rp:        l2 = rl + 1
else:                    l2 = 0
persist (p2, l2) before acknowledging the mutation
```

Overflow is an explicit error/rebase path, not integer wrap. All comparisons and serialization use fixed-width unsigned values and golden boundary tests.

### Clock trust and unknown time

- Website mutations are stamped in the authoritative server transaction; a browser-supplied clock is ignored.
- Device time uses the same frozen six-value evidence vocabulary as Track v3: `unknown`, `approximate_persisted`, `server_anchored`, `sntp_synced`, `gnss_trusted`, or `legacy_minute`. Only `server_anchored`, bounded `sntp_synced`, and `gnss_trusted` may author the HLC physical component, and only within the server's ±600-second skew window. `unknown`, `approximate_persisted`, and `legacy_minute` rebase at server acceptance. SNTP is not treated as authenticated merely because it returned a packet.
- The device HLC never moves backwards. It persists the last trusted physical component and increments logical order for later local mutations even through reboot.
- The server bounds any device physical value against policy and its last server/device anchors. A value too far in the future cannot dominate indefinitely.
- Unknown/out-of-policy device time is deterministically rebased at authenticated server receipt, preserving the collar's persisted local mutation sequence and recording `time_rebased=true`. Identical replay reuses the first result.
- UI/audit must disclose rebased/uncertain ordering. If an AP edit and web edit occurred offline without comparable trusted clocks, receipt-time rebasing is the deterministic fallback, not proof of real-world “last edit.”

### Mutation and convergence behavior

#### Local AP mutation

1. Parse the complete target resource and validate it with the same firmware semantic rules used today.
2. Advance the device HLC and create a stable mutation ID.
3. Persist resource value, HLC, pending mutation, hash, last applied server version, and relevant sync metadata atomically in a new CRC/A/B configuration envelope.
4. Only after verified persistence, publish/apply it to runtime.
5. On next sync, submit the pending mutation until the server returns its stable outcome.

The existing local HTTP contract remains available when cloud is off. All local writers must eventually pass through one mutation/validation/commit service; otherwise AP and cloud paths can diverge.

#### Website mutation

1. Authenticate the user and authorize the collar/dog/resource role.
2. Validate the entire resource against the collar's reported capabilities/schema.
3. In one transaction, assign server HLC/actor, compare total-order key, append the revision, and update current desired state only if it wins.
4. Return winner, `server_version`, and whether the submitted mutation won. A stale `base_server_version` produces explicit stale-editor feedback but does not replace deterministic LWW with an arbitrary rejection.

#### Device sync/apply

1. The server transaction first evaluates uploaded local mutations and telemetry idempotently.
2. The response returns the canonical winner for each requested/supported resource, including its schema, HLC, hash, and `server_version`.
3. The collar validates a downloaded winner and commits it through the same A/B path before applying it.
4. On a later/current sync it reports `pending`, `applied`, `rejected`, or `unsupported`, including the exact desired `server_version` and a bounded reason code.
5. The website distinguishes desired from reported/applied. Downloaded does not mean applied.

An invalid or unsupported remote value never silently falls back to defaults and never corrupts last-known-good local state. It remains desired at the server with a visible rejection until changed or capability support appears.

### Idempotency and response semantics

- `(actor_id, mutation_id)` is unique. The same ID/body hash returns the recorded result; the same ID/different hash is a protocol error.
- Same resource value/body hash is a no-op and does not manufacture a new server version unless audit policy explicitly records the attempted mutation separately.
- A normal older LWW mutation is a successful, resolved operation with `won=false` and the winner returned; it is not an HTTP `409`.
- A consolidated `device-v1-sync` may commit telemetry while individual config resources win, lose, or reject. The HTTP success contains per-resource outcomes. Request-level failure is reserved for authentication, envelope/schema/size, idempotency-hash conflict, or transactional failure.
- Capability negotiation prevents sending a schema a collar cannot parse. Unknown additive response fields are ignored; unknown required schema versions are reported unsupported.

## Consequences

### Positive

- Unrelated configuration areas do not overwrite each other.
- Coupled arrays/gates remain valid and atomic.
- HLC preserves deterministic causality/order through offline operation better than wall-clock-only LWW.
- Desired/reported separation prevents a website from falsely claiming a setting is active.
- Replay and power loss converge without double mutations.

### Costs and limits

- `RuntimeConfig` persistence must evolve to include sync metadata without weakening its existing A/B guarantees.
- A real-time “last edit” cannot be proven for mutually offline, untrusted clocks; rebasing is a documented approximation.
- Resource/schema migrations and capability negotiation add ongoing compatibility work.
- LWW intentionally discards a losing concurrent value; revision history is needed for explanation/recovery.

## Rejected alternatives

- **Whole-document LWW:** unrelated stale fields overwrite newer values.
- **Per-field LWW everywhere:** can create invalid ranges/effect/profile combinations and bloats metadata.
- **Server-arrival-order only:** systematically misorders long-offline edits and hides original causality.
- **Device wall-clock timestamp only:** a bad/future clock can win forever.
- **Optimistic `409` for every stale base version:** does not converge unattended devices and contradicts the chosen LWW product rule.
- **Treat response/download as applied:** creates false device state after validation/storage failures.
- **Remote Home/power in the first release:** unnecessary privacy/safety risk before the foundation is proven.

## Implementation and acceptance gates

This ADR specifies future behavior; current firmware and website do not implement it. Phase 0/1 contracts and Phase 2/4 code must test at minimum:

1. AP-before-web, web-before-AP, simultaneous/equal physical time, multiple offline edits, delayed sync, duplicated/out-of-order responses, reboot at each persistence boundary;
2. unknown, stale, future, backward, GNSS-trusted, bounded-SNTP, and server-anchor clock cases plus logical overflow boundaries;
3. every lexicographic tie and the published HLC vectors in [`contracts/device-v1/hlc.md`](../../contracts/device-v1/hlc.md);
4. same mutation replay, same ID/different hash, no-op body, stale base version, unsupported schema, validation/persistence rejection;
5. atomic preservation of speed profile and GPS resource invariants under power cuts;
6. desired versus pending/applied/rejected UI truth;
7. proof that Home, power calibration, Wi-Fi/AP credentials, and PIN never appear in cloud requests/database/logs, and that the device credential appears only transiently in the verified-TLS claim body or sync/revoke Authorization header while persistent server state/logs contain only its digest/redacted identity.
